一、项目摘要

校园创意验证 Agent 面向希望把校园生活中的小问题转成可验证项目的学生个人或小团队。它帮助使用者从一个自然语言需求开始，先明确服务对象和已掌握证据，再由规划 Agent 形成低成本验证计划，由方案 Agent 整理成项目草案，最后由独立验证 Agent 检查内容完整性与证据边界。如果检查未通过，系统进入 Self-Loop，根据问题有限次修订，再输出方案、检查报告和完整运行日志。

很多校园项目在立项时容易跳过需求验证，直接设想功能、规模和效果。学生个人投入有限，早期如果把未经证实的判断写成用户事实，后续容易开发出无人使用的产品，也会在参赛材料中误报效果。本项目把“先验证问题，再决定是否扩大投入”落实为一条可运行的 Agent 工作流。应用要求输入者说明具体问题和目标用户；证据可以暂时为空，但输出会明确提示“待验证”，不会用模拟数据填补空白。

当前 MVP 提供模拟模式和真实模型 API 模式。模拟模式使用确定性的本地逻辑，只用于展示页面、编排步骤、日志与导出，不调用大模型，也不会被描述成真实模型效果。真实模式按 OpenAI Chat Completions 兼容协议分别调用规划、方案、验证与修订步骤；密钥只从环境变量读取。系统最多进行两次返工，避免模型循环失控。用户可以下载 Markdown 报告和 JSON 运行记录，便于复核、留档和演示。

项目定位为参赛创新应用原型和方法验证工具，不宣称已在校园部署，也不宣称已经取得用户增长、节省时间或商业收入。下一阶段需通过真实用户访谈验证目标用户的痛点，通过 API 实测确认真实模型编排稳定性，并依据官方赛题要求准备申报材料。

二、问题背景与目标用户

2.1 需要解决的问题

校园创新想法通常来自办事信息难找、课程资源分散、社团活动组织繁琐、校园生活服务不清楚等日常经历。学生能够快速提出功能设想，却不一定有时间或方法确认问题是否普遍、用户是否愿意改变习惯、最小方案是否可操作。个人参赛者还需要同时完成需求分析、产品设计、技术搭建、过程记录和展示材料，往往在项目初期就面临能力跨度大、验证成本高的问题。

本项目聚焦的核心问题不是“如何让模型替学生创业”，而是“怎样让个人创意者用一条可见、可复核的流程，把模糊想法变成可以在几天内验证的假设”。系统引导使用者区分四类信息：用户原话或观察事实、已有证据、需要验证的假设、模型提出的建议。四类信息在方案中保持可辨识，评委和使用者可以看到结论从哪里来。

2.2 目标用户

第一类用户是有校园服务或校园内容项目想法的个人参赛学生。他们需要在有限时间内判断是否值得继续开发。第二类用户是课程实践或创新创业活动中的学生小组，他们需要形成访谈提纲和小规模试验计划。第三类用户是创新指导教师或项目导师，他们可将该工具用于检查学生是否提供了需求证据以及指标是否可以观察。

MVP 首先服务个人参赛学生。产品不依赖复杂帐号、团队权限或校园数据接入，降低部署门槛。用户只需浏览器和 Python 环境就能本地启动。产品暂不面向企业经营决策、医疗、金融等高风险场景，也不处理学生个人敏感资料。

2.3 用户任务与价值

用户输入问题描述、目标用户和已有证据。系统输出简短的验证目标、关键假设、访谈建议、成功指标、风险提醒和方案草案。用户可以据此先与真实同学交流，再补充证据重新运行流程。实际价值需要用后续试点测量，当前的产品价值主张是帮助个人参赛者把早期讨论集中在可观察的证据与下一步行动上。

三、产品设计与核心流程

3.1 工作流概览

产品采用有限步骤的 Agent 编排，而不是让单个提示词同时完成所有工作。主流程为：输入校验 → 规划 Agent → 方案 Agent → 独立验证 Agent → 有上限的 Self-Loop → 结果展示与导出。每个环节有明确输入和输出，日志记录步骤名称、状态、说明和耗时。

第一步是输入校验。系统要求问题描述和目标用户不能为空，已有证据为可选项。系统提醒用户不要输入姓名、手机号、身份证号等敏感信息。输入不足时，页面直接提示补齐必要内容，不启动后续模型调用。

第二步是规划 Agent。规划 Agent 根据用户问题、目标用户和证据提出一句话目标、最多三个关键假设、短周期验证步骤、访谈问题、成功指标和风险。它必须区分用户已经提供的事实和模型提出的待验证假设。如果没有证据，计划会建议采集证据，而不能声称用户需求已被证明。

第三步是方案 Agent。方案 Agent 把输入和规划结果整理为结构化草案，包括用户痛点与证据、验证计划、最小可行方案、目标指标和风险边界。它的提示约束禁止编造访谈数量、用户反馈、市场规模或试点成效。

第四步是独立验证 Agent。验证 Agent 单独检查方案是否包含要求章节，是否把缺乏证据的推测写成事实，是否有可操作的验证步骤和可观察指标。真实模式下该步骤使用独立模型调用，输出结构化 JSON，包含是否通过、问题列表、缺失章节和摘要。模拟模式使用确定性规则，界面明确标明模拟。

第五步是 Self-Loop。若验证不通过，系统把问题列表传回方案修订步骤，要求保留真实信息并修复缺陷。最多返工两次，然后再做独立验证。达到上限仍未通过时，系统如实展示未通过状态和问题，不伪造成功。此机制既展示闭环编排，也提供明确的终止条件。

最后，页面展示规划结果、检查报告、方案、每个步骤的日志，并允许下载 Markdown 和 JSON。用户可检查方案、修改输入，再次运行。MVP 暂不自动提交报名系统，也不自动发布任何对外内容。

3.2 Agent 角色和 I/O 约定

规划 Agent 的输入字段为 problem、audience、evidence；输出为 plan 文本。方案 Agent 的输入字段为相同用户信息及 plan；输出为 solution 文本。验证 Agent 的输入字段包括用户问题、目标用户、证据和 solution；输出为 passed、issues、missing_sections、summary。修订 Agent 的输入字段是原方案、验证问题和用户输入；输出为完整修订方案。每个 Agent 的结果都由编排器控制传递，不允许 Agent 修改全局运行状态或任意访问文件。

角色划分使得不同任务能够独立调整。后续可以分别评估计划质量、方案事实表达和验证准确率，而不是只比较一段最终回答。编排器负责顺序和停止条件，Agent 负责局部任务，网页负责展示和用户输入，模型客户端负责协议调用。

3.3 MVP 不包含的功能

当前版本不包含自动联网搜索、文件知识库、校园账号登录、团队协作、项目审批、付款或自动部署。内置四条项目验证指南采用关键词匹配，属于轻量本地检索基线，不是语义向量检索。它不声称对事实进行外部查证，也不提供任何“市场已验证”结论。外部搜索会引入来源筛选、版权和内容时效问题，需要单独设计来源引用和人工审核，不能为演示效果而假装已完成。

四、技术方案

4.1 技术栈

MVP 使用 Python 3、Streamlit 和 Python 标准库。Streamlit 提供本地网页交互，降低前端开发和部署复杂度。核心编排放在 core.py 中，与网页入口 app.py 分离，方便测试和后续重构。模型调用由 LLMClient 统一处理，使用 urllib 请求兼容接口，不在代码中硬编码密钥。结果以字典结构保存于当前会话，并可序列化为 Markdown 或 JSON 文件。

选择轻量架构是为了控制个人参赛者的开发负担。MVP 暂不引入数据库和复杂 Agent 框架，因为目前流程只有四种角色、有限状态传递和明确的重试上限。若后续评测表明需要并发 Agent、工具权限管理或复杂工作流，再考虑引入框架；届时以实际需求和可维护性为依据。

4.2 Agent 注册与任务派发

Agent 注册表 `agent_registry.json` 记录每个角色的稳定 ID、显示名称、职责、能力标签、配置负载、经验分、优先级、版本和角色提示。`scheduler.py` 在执行前根据当前任务内容构造能力需求。例如，包含已有证据时，规划任务增加 evidence 能力要求；方案涉及数据、测试或成效时，增加 metrics 要求；出现产品或流程设计时，增加 product 能力要求。验证任务会按证据输入增加 evidence 能力，按指标内容增加 metrics 能力。

对每个同职责候选 Agent 计算：`调度分 = 能力覆盖率 × 100 + 经验分 × 10 + 优先级 − 配置负载 × 20`。能力覆盖率等于候选 Agent 覆盖的必需能力数除以任务必需能力数；配置负载和经验分限制在 0 到 1。系统选择得分最高的启用候选项，并在运行日志中保留所需能力、覆盖比例和配置负载。注册表可通过编辑 JSON 增加、禁用或调整候选项；应用每次运行读取配置，不需要修改编排器逻辑。

这是一个可解释的单机调度基线，不是在线资源调度器。配置负载是注册表中的静态值，尚未连接真实 CPU、并发数、API 额度或响应时延；当前任务仍按依赖关系顺序执行，没有并行分支、队列抢占、DAG 工作流或失败节点回滚。下一步要用相同任务集对比固定派发与能力派发，记录任务成功率、调度选择、耗时和返工数，再决定是否需要实时负载或并行调度。

4.3 真实模型 API

真实模式支持 OpenAI Chat Completions 兼容接口。用户通过 OPENAI_BASE_URL 和 OPENAI_MODEL 选择服务地址与模型，通过 OPENAI_API_KEY 环境变量提供密钥。默认地址和模型仅作为示例，实际使用前应确认服务商的接口协议、模型名称、配额、费用与数据处理条款。程序不会把密钥写入代码、输出报告或 JSON 运行记录。

每次 API 调用设置超时，并把 HTTP 状态或网络错误转换为易读的页面提示。当前版本没有自动重试网络请求，避免意外重复计费；Self-Loop 只在验证 Agent 返回有效但未通过的结果时触发。未来若增加网络错误重试，应设置次数限制和费用提示。

4.4 可观测性

每次运行日志记录 Agent 名称、状态、摘要和耗时。总流程记录模型模式、生成时间和返工次数。报告中带有模式字段，评审可区分模拟流程和真实模型输出。对于模拟模式，界面固定显示醒目标识；不得用模拟模式制作“真实 API 成效”或模型能力证明。

现有运行数据不含密钥。用户输入会进入真实服务商 API 请求，因此真实模式下应只输入必要的非敏感材料，并依据服务商条款确认数据处理方式。应用不写入长期数据库，刷新会话可能使网页中结果消失，应及时下载报告。

五、创新点与项目特色

第一，项目把 Agent 编排本身作为可理解、可观察的产品流程。规划、方案、验证和修订分别承担职责，每步输入输出清晰，日志让用户看到运行轨迹。

第二，系统将证据边界作为方案质量的核心检查项。它允许用户暂时没有证据，但要求方案把相关内容标成待验证，并提示先做访谈或小测试。对于早期创新项目，这能降低模型把常见推测包装成调研结论的风险。

第三，Self-Loop 有明确的验证信号、有限次数和停止条件。每次返工依据独立验证 Agent 的问题列表；超过最大次数仍有问题时展示失败状态。这比无边界的重复生成更容易观察和评测。

第四，模拟模式和真实模型模式严格区分。模拟模式在页面、导出报告中均标明，不需要 API Key 即可体验完整界面与流程；真实模式明确走配置的 API。该安排让开发教学和竞赛演示可以在密钥不可用时继续，同时避免将模拟内容误报为模型结果。

第五，产品把复杂需求压缩为个人可完成的小规模验证行动。它不要求先做完整平台，而是建议先用访谈和人工原型确认用户是否愿意尝试，再根据结果决定是否继续开发。

六、应用场景与使用示例

假设一名新生提出“办事信息分散，补办校园卡时不知道去哪找”。目标用户为刚入学的新生，已有证据可以填写访谈或观察记录，也可以暂时留空。规划 Agent 生成待验证假设和访谈问题，例如询问最近一次查找信息的过程、遇到的阻碍和目前使用的渠道。方案 Agent 建议先构建人工整理的办事信息页面原型，不急于开发智能问答系统。验证指标可以包括用户是否独立找到正确办事入口、完成任务所需时间、是否愿意再次使用。验证 Agent 检查方案是否把五位用户测试写成目标而非既有结果，并检查风险章节。

这个场景仅用于说明操作方式，不是已完成的真实访谈案例。正式参赛材料应由参赛者补充实际调研记录、经同意的匿名反馈、测试过程和原始结果。未开展的活动必须写成计划，不得在展示中以完成时态表达。

可延伸场景包括社团活动信息整理、课程资料索引、校园闲置物品交换、学生志愿服务匹配等。每个场景都应先验证具体用户和真实流程，再决定是否适合 Agent 自动化。产品不应把“用了大模型”本身当作用户价值。

七、评测设计与成功指标

当前尚无真实用户试点结果，下面指标是下一阶段的评测设计和目标，不是已经达到的成果。

产品流程可用性：邀请至少五名目标用户完成一次需求输入和结果理解任务，记录是否能独立完成、在哪一步困惑、是否理解模拟与真实模式区别。初步目标是五人均能完成输入并找到最终方案下载入口，问题需逐条记录，不以小样本结果推断全校用户。

规划质量：由两名人工评审按假设清晰度、验证步骤可执行性、指标可观察性、证据区分四项进行评分，使用五分制。报告均分、分歧和样本量，不只展示均值。若无法邀请第二位评审，应如实说明由单人评审，结论只供内部改进。

验证准确性：准备不少于十个测试用例，覆盖缺失章节、证据不足、目标用户不明确、结论夸大、格式错误和通过样例。记录验证 Agent 的正确拦截数、漏报数和误报数。真实模型应记录模型名、运行日期与输入输出摘要，移除个人敏感信息。

稳定性：在可控网络环境下至少运行二十次流程，记录成功率、超时数、解析失败次数、平均时长和返工次数。模拟模式用于测试界面和流程稳定性，不能替代真实 API 的运行数据。模型供应商可能变化，运行结果具有版本和时间依赖。

成本观察：真实 API 模式下记录每次调用数量、估算输入输出 token 和服务商账单数据。未核实价格前，不写具体单次成本。设置调用预算上限、最大重试次数和请求超时，避免测试时产生意外费用。

八、安全、隐私与伦理边界

应用提醒用户不要输入个人敏感信息。真实 API 模式会将需求文本发送给配置的第三方模型服务，因此参赛者应取得必要授权，删除身份信息，并按服务商条款处理。MVP 不做持久化存储，也不对模型服务商的数据保留策略作未经核实的承诺。

模型可能生成错误信息、遗漏条件或输出不适合实际执行的建议。当前验证 Agent 做的是结构和文本边界检查，不是外部事实核查。方案中涉及学校办事规则、收费、政策、法律和安全的内容，需要用户通过学校官方渠道核验。系统应将输出定位为草案和行动建议，不作为最终决策。

项目不采集未成年人数据，不针对个人作评价，不自动联系用户或发布内容。未来如果接入问卷、校园平台或自动化工具，应额外评估授权、最少数据原则、撤回机制和人工确认点。

九、商业与落地路径

短期落地路径是个人电脑本地运行和校园创新工作坊试用。若用户反馈证明该工具能改善需求验证过程，再考虑为创新创业课程提供教师版工作流、项目模板和过程记录功能。可探索按课程或机构授权、活动部署支持等方式，但收入模式尚未验证，不在当前阶段承诺市场规模或商业回报。

推广先通过与创新创业课程、社团和导师合作开展小规模体验，收集匿名使用反馈和任务完成记录。数据使用应事先告知并征得同意。试用结束后公开方法和局限，避免把参赛演示当作广泛部署证明。

十一、风险与应对

赛题覆盖不足：固定工作流不能代替完整动态调度平台。当前能力匹配派发尚未加入并行/DAG和实时负载采集，接下来验证该策略并补工具调用和验证对照；未实现的知识库、工作流画布等在材料中明确标示，不夸大完成度。

个人开发时间不足：网页和模型 API 对参赛者都是新内容。采用轻量技术栈，先确保本地可运行和完整流程，再增加调研、材料和视觉完善。若进度压缩，优先保证真实模式可演示、证据不造假、提交文件齐全。

API 不稳定或费用增加：使用模拟模式做界面演练，真实演示前检查余额、网络和模型名；按当前实现，单次真实模式最多调用模型 7 次：规划 1 次、初稿生成 1 次、验证最多 3 次、返工生成最多 2 次；验证提前通过时调用次数更少。记录运行账单，避免隐藏成本。

模型输出不可靠：分阶段提示、独立验证、有限返工和人工核查共同降低风险。独立验证同样可能犯错，不能把通过状态当作真实信息证明。

调研样本偏少：把结果作为早期探索而非总体结论，保留样本数、招募方式和问题文本，并说明偏差。没有用户测试时只提交计划，不声称产品已验证。

展示与成品不一致：演示录像使用当前版本现场运行，保存同一版本源码和输入样例。预录内容需注明剪辑，不以动画或静态原型替代功能演示。

十二、交付清单与验收标准

可运行应用包含 app.py、core.py、依赖文件、密钥示例文件、启动 README 和自动化测试。验收时应在全新 Python 环境安装依赖、成功启动本地网页、以模拟模式完成流程、确认模拟标识和下载报告可用。配置 API Key 后，真实模式应成功调用模型，报告应标注真实模式，且密钥不得出现在日志或导出内容中。异常情况下应显示易懂的错误提示。

参赛材料至少包含作品介绍文档、演示视频、官方要求的作品简介和承诺材料，以及选填支撑文件。赛题一初赛材料包括PDF方案书（不少于5000字）、10–15页方案讲解PPT、3–5分钟演示视频和可复现代码仓库或在线演示。当前工作交付包含方案书源稿与PDF、演示稿、脚本草案和本地代码包；尚未提供公开源码仓库/在线演示地址，也没有视频成片。发布仓库、报名信息和录制视频仍是待完成事项。所有匿名化、肖像授权和访谈引用应遵循受访者同意范围。

十三、结论

校园创意验证 Agent 将校园问题发现后的早期验证过程组织成一条有角色分工、独立检查、有限返工和可观测日志的多Agent工作流。该MVP已可本地运行，覆盖赛题核心链路的一部分；并行/DAG调度、外部工具集成、真实模型实测、用户试点和公开仓库/在线演示仍待完成。说明会要求提交材料清楚展示系统可运行和过程可复现，因此下阶段要优先补齐这些可验证成果。

本项目不承诺获奖，也不把工具生成的方案当作调研成果。参赛者需要用真实的校园观察和测试结果证明需求，再据官方赛题要求调整最终版本。项目的可信度取决于可复现的运行过程、准确披露的证据和对限制的清楚说明。
